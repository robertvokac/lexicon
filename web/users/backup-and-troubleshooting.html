Backup & troubleshooting

Lexicon keeps structured data in one SQLite file and optional attachment files beside it. Copy both for a complete backup — or let the server do it for you.

Data location

WhatWhere
Database filelexicon.db
Blob attachmentsblobs/ next to lexicon.db, organized by SHA-256 hash
LocationThe same directory as the Lexicon executable
FormatStandard SQLite 3 — readable with any SQLite tool
ℹ️

Portable by design Move lexicon.db and the adjacent blobs directory together, placing them next to the executable on the other machine.

Backup strategies

The SQLite database and Blob directory together form the complete Lexicon data set. Backing up only the database is not sufficient when Blob Fields are used. Prefer a backup while Lexicon is closed or a coordinated snapshot while data is not changing.

  1. Close Lexicon. This guarantees the database is not mid-write.
  2. Copy lexicon.db and blobs/ to safe storage — external drive, NAS, or a synced folder.
  3. Version your backups — keep dated snapshots (daily or weekly) instead of overwriting a single copy: 
    mkdir -p ~/backups/lexicon-$(date +%F)
cp lexicon.db ~/backups/lexicon-$(date +%F)/
cp -a blobs ~/backups/lexicon-$(date +%F)/
💡

Automate it A scheduled copy of the database and blob directory protects both metadata and attachments. If your lexicon is mission-critical, back up more often.

Automatic backups on the server

If you run LexiconServer, it can do the whole job for you. Give it a directory and it backs the dictionary up on its own:

LexiconServer --database ~/lexicon/lexicon.db --backup-dir ~/lexicon-backups
  • Every 24 hours by default (--backup-interval H), keeping the newest 14 backups (--backup-keep N); older ones are removed.
  • Each backup holds a consistent copy of the database taken while the server keeps running, a portable JSON export, and the blob files the dictionary refers to.
  • Files that did not change are shared between backups through hard links, so fourteen backups cost far less than fourteen copies.
  • LexiconServer backup --backup-dir DIR makes one on demand — handy before an upgrade.

Export and import

A backup of the raw files is the safest copy; an export is the portable one:

  • File → Export... writes the whole dictionary as one documented JSON file, optionally with the files its blob and image values refer to.
  • File → Import... merges such a file into the open dictionary: groups, types and fields are matched by name, and items that are already there are left untouched.
  • The web client and the Android app offer the same two actions, and LexiconServer export and LexiconServer import do it from the command line.
  • Alarms, review dates, links, metadata, cards and their quiz counts all travel with it. Export format version 2 includes cards; older Lexicon releases refuse that version instead of silently dropping them. See the export format.

Deletion safety rules

Blob files are deduplicated by SHA-256: multiple Item values can refer to the same physical file. Removing a value, Item, Field, or Type leaves the file in place. Use Tools → Blob maintenance… to scan for unused files. A normal Scan checks references and paths; Full integrity check also hashes file contents. Missing means a referenced file is absent; Hash mismatch means its contents are corrupt. Restore these from backup rather than deleting them. Only the explicitly confirmed Delete unused blobs action removes canonical, still-unreferenced files after rechecking references and contents. Unexpected files and symlinks are reported but not collected.

Lexicon uses cascade deletion to keep the database consistent. Know the two rules before you delete anything:

⚠️

Deleting an item also removes its aliases, tags, flags, properties, custom field values, cards, and all links/backlinks pointing to or from it.

⚠️

Deleting a group removes every item inside it — including all of their content and metadata. This is the most destructive action in the application.

Deleting a type clears its assignment and custom field values on affected items after confirmation. There is no undo for deletions. Back up lexicon.db and blobs/ first if unsure.

Troubleshooting

The app does not start

  • Verify that the Qt 6 runtime is installed and matches the version Lexicon was built against.
  • Ensure native SQLite and OpenSSL Crypto libraries are present.

Database errors on startup

  • Check that the directory containing the executable is writable — Lexicon needs to create and update lexicon.db there.
  • Make sure lexicon.db is not locked by another process (another running Lexicon instance, a DB browser, or a sync tool holding the file).

The build fails

  • Confirm your compiler supports C++23 (recent GCC, Clang, or MSVC).
  • Confirm CMake can find Qt6::Core and Qt6::Widgets, plus SQLite and OpenSSL Crypto — set CMAKE_PREFIX_PATH to your Qt installation if needed.
  • See the developer build guide for platform details.

Still stuck?

Open an issue on GitHub with your OS, Qt version, and the exact error message.
